# Formal model (bounded research model)

Analyze each reachable path through a recognized `@agent` entry point. Events are `source(kind,x)`, `boundary(kind,x,y)`, and `sink(kind,x)`. Values carry a product domain: origins ⊆ {LLM, external, user, local-sensitive}; trust ∈ {Trusted, Untrusted, Unknown}; confidentiality ∈ {Public, Sensitive}; validation ∈ {yes,no,unknown}; authorization ∈ {yes,no,unknown}; and effects ⊆ {LLM_CALL, EXTERNAL_READ, EXTERNAL_WRITE, PRIVILEGED_ACTION, HUMAN_APPROVAL}. Joins union origins/effects, take Sensitive if either operand is sensitive, and retain a boundary flag only when present on both paths. Unknown propagates for unresolved origins/targets. This is a may-flow analysis; implicit control dependence and object aliasing are currently outside its proved subset.

P1: for every reachable privileged sink with an argument causally derived from LLM output, the exact argument must have passed a trusted validation or sanitization boundary. P2: for every reachable external model/tool sink, no sensitive argument reaches a destination lacking an explicit authorized-recipient contract. P3: every reachable critical external action must consume the payload returned from a trusted authorization or human-approval boundary. An earlier unrelated approval does not suffice.

`PROVED` means all reachable paths in the modeled, closed-world subset satisfy the property and no relevant uncertainty remains. It is conditional on the stated API/boundary contracts. `VIOLATED` means a concrete syntactic feasible path within that model exhibits a counterexample; infeasible branch correlations can cause false alarms. `UNKNOWN` means neither proof nor a model counterexample is justified, and the diagnostic gives the unsupported construct and location. In this conservative implementation, relevant unsupported behavior takes precedence over a modeled counterexample, so the result is `UNKNOWN` if both occur. This loses a certain violation in exchange for avoiding a misleading claim about the whole path. No `PROVED` claim is made from absence of known sinks if an opaque effect could hide one. Results are separate per property.

No arbitrary Python program is soundly decided by this analyzer. In particular `validate`, `sanitize`, `authorize`, `human_approve`, `llm`, `external_llm`, `external_tool`, `payment.execute`, `db.mutate`, `fs.write`, `sensitive_data` are modeled *only* when those names resolve to immutable, independently audited capabilities. The prototype does not check that premise. Annotation names, function bodies and decorators alone are not security boundaries in real Python. Both exception control flow and calls through unknown code are conservative uncertainty. The IR preserves AST nodes plus statement location and named effects; the evaluator propagates abstract values and path states across branches and local calls.
