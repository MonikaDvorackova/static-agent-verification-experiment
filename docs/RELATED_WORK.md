# Related work and novelty check (22 September 2026)

Columns: property / enforcement / LLM nondeterminism / information flow / capabilities / approval / provenance / limitation. These are descriptions of the cited authors' stated scope, not independently reproduced guarantees.

| Work | Property and enforcement | LLM uncertainty / flow | Capabilities / approval | Provenance / limitation |
|---|---|---|---|---|
| Classical IFC and effect systems | Static security labels and typed effects under language assumptions | Treat model outputs as untrusted; track declared flow | Effects and authority can be types | Depends on trusted primitives, sound semantics and complete mediation |
| Pysa / PyFlow | Static Python source-to-sink analysis | May-flow approximations; no proof of model meaning | Requires custom models for gate semantics | Existing serious baseline; our toy implementation has no performance or accuracy claim ([Pysa](https://github.com/facebook/Pysa), [PyFlow](https://arxiv.org/abs/2608.07026)) |
| [FIDES](https://www.microsoft.com/en-us/research/publication/securing-ai-agents-with-information-flow-control/) | Agent planner confidentiality and integrity through dynamic IFC | Labels propagate across planner execution despite nondeterministic output | Planner restrictions and controlled access | Runtime protection under instrumentation; not ordinary Python static proof |
| [CaMeL](https://github.com/google-research/camel-prompt-injection) | Constrained planner and runtime tool mediation for prompt injection | Untrusted data kept separate from control through runtime tracking | Explicit security policy and tool control | Depends on interpreter and tool mediation |
| [Cleat](https://cleat.sh/docs/) | Agent container isolation and hash-bound command approval at runtime | Does not statically prove LLM output safety | Sandbox capabilities and user approval | Execution isolation; not static Python information-flow verification |
| [Harn](https://github.com/burin-labs/harn) | Agent language/runtime and effect-grant trust records | Language contracts constrain agent effects; semantics require further evaluation | Effect grants and approval gates | Records autonomy decisions; no claim here of whole-Python proofs |
| [Aegis (Yuan et al.)](https://arxiv.org/abs/2603.12621) | Pre-execution firewall on tool calls | Inspects actual model-generated calls | Policy checks and human escalation | Signed/hash-linked audit; runtime interception, not static code proof |
| [Aver](https://github.com/jasisz/aver) | Language for auditable AI-written code, verification targets | Focus appears to be generated-code verification, not established agent IFC | Effect/spec constructs; details need independent evaluation | Early project; name is ambiguous and security guarantee not established here |
| [ArgorixLang](https://github.com/argorixlabs/argorixlang) | Compiled agent language with semantic checks and VM | Constrains execution boundaries rather than proving model truth | Declared agent capabilities and policy bindings | Offline-verifiable evidence; source integrity outside described bundle verification ([paper](https://papers.ssrn.com/sol3/papers.cfm?abstract_id=7016202)) |
| General agent security frameworks | Runtime guardrails, sandboxing, policy engines and tool proxies vary | Usually inspect actual nondeterministic tool calls | Often mediate capabilities and approval | Runtime coverage depends on integration and bypass resistance |

Our combination of three policies and explicit `UNKNOWN` is an experiment in precision and failure modes, **not** evidence of conceptual novelty. Static taint systems with custom source/sink/sanitizer models already cover much of P1 and P2. P3 needs binding of authority to a particular payload and action, which the present prototype only approximates by value propagation.
