# Language justification

The new 20-case SDK-shaped corpus is deliberately authored: under a sealed-contract premise its narrow adapter matches 60 conditional labels, while a configured Pysa baseline detects 4/4 known P1 violations, 3/3 known P2 violations and 4/8 known P3 violations. A CodeQL run and independent evaluation on real agent code are still missing (`SDK_PROFILE_EXPERIMENT.md`).

Current evidence does not justify inventing a new programming language. A configured Pysa run independently detects the elementary P1 and P2 flows and some P3 cases (see `BASELINE_COMPARISON.md`). Its particular P3 taint rule misses constant actions and modified approved data. Three unmodified agent-framework examples yield 9/9 UNKNOWN with this prototype (`PUBLIC_CODE_EXPERIMENT.md`). Static information flow, effect typing and capabilities are established techniques; Python's open-world dynamism limits unconditional proofs. A useful next step is a restricted Python subset plus audited capability interfaces and a runtime enforcement point, with measured unknown rates. Only if those restrictions impose unacceptable escape hatches or ergonomics should a language be considered. The smallest *semantic* requirements, if they cannot be met acceptably in existing systems, are sealed capability imports and nonforgeable effect tokens; typed confidentiality/integrity labels with explicit declassification and endorsement; and single-use approval tokens tied to a specific action, arguments and context. Scala 3 capture checking already provides static capability tracking, and runtime mediators can bind an approval at execution time. The research has not shown that these must require a new language. These are semantic requirements, not proposed syntax. Even such a language cannot prove human intent, model truthfulness or external-service behavior.
