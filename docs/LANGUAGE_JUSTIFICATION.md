# Language justification

The new 20-case SDK-shaped corpus is deliberately authored: under a sealed-contract premise its narrow adapter matches 60 conditional labels, while a configured Pysa baseline detects 4/4 known P1 violations, 3/3 known P2 violations and 4/8 known P3 violations. A three-project selected-path study found two direct CodeQL file-write flows and one scheduled-helper edge; both versions of our analyzer returned UNKNOWN on every unchanged module. This does not establish independent application-level ground truth, whole-project CodeQL P1–P3 judgments or a real-world Pysa comparison (`SDK_PROFILE_EXPERIMENT.md`, `REAL_WORLD_CODEQL_EXPERIMENT.md`, `MULTI_PROJECT_BENCHMARK.md`).

The six-case follow-up in `P3_BINDING_EXPERIMENT.md` isolates a stricter P3*: one authentic, fresh approval must bind the concrete action, target, arguments and context and be consumed exactly once through a complete mediator. Our analyzer returns conditional `PROVED` for the nominal matching-action case, but cannot establish P3* even there. This is evidence of an **unverified premise**, not evidence that Python fundamentally prevents implementing a trustworthy mediator or that Scala capabilities alone suffice. No executable Scala comparison was performed in this follow-up.

An ensuing offline SDK 0.22.3 probe in the same document observed that a rejected tool call did not execute, an approved call executed once, and two separate restorations of one approved pending state executed twice. It does not establish a general SDK vulnerability: an external exactly-once store or idempotent effect can address this; the experiment did not test Scala.

The subsequent `CAPABILITY_COMPARISON.md` records an executable Scala 3.9.0 experiment: the typed-capability example compiled; missing authority, leaking a capability into a pure callback and an unchecked cast in safe mode failed compilation. An in-memory application effect ledger collapsed two SDK resumptions into one effect but a direct call bypassed SDK approval. This strengthens the case for established static capability constraints **together with** a runtime effect mediator. It still does not demonstrate complete mediation, authenticated approval, or exact-once behavior across process crashes, and it supplies no justification for new language syntax.

Current evidence does not justify inventing a new programming language. A configured Pysa run independently detects the elementary P1 and P2 flows and some P3 cases (see `BASELINE_COMPARISON.md`). Its particular P3 taint rule misses constant actions and modified approved data. Three unmodified agent-framework examples yield 9/9 UNKNOWN with this prototype (`PUBLIC_CODE_EXPERIMENT.md`). Static information flow, effect typing and capabilities are established techniques; Python's open-world dynamism limits unconditional proofs. A useful next step is a restricted Python subset plus audited capability interfaces and a runtime enforcement point, with measured unknown rates. Only if those restrictions impose unacceptable escape hatches or ergonomics should a language be considered. The smallest *semantic* requirements, if they cannot be met acceptably in existing systems, are sealed capability imports and nonforgeable effect tokens; typed confidentiality/integrity labels with explicit declassification and endorsement; and single-use approval tokens tied to a specific action, arguments and context. Scala 3 capture checking already provides static capability tracking, and runtime mediators can bind an approval at execution time. The research has not shown that these must require a new language. These are semantic requirements, not proposed syntax. Even such a language cannot prove human intent, model truthfulness or external-service behavior.
